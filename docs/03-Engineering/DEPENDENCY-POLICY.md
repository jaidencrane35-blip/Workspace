# Dependency Policy

| Field | Value |
|-------|-------|
| **Purpose** | Define rules for adding, auditing, and managing third-party dependencies |
| **Owner** | Lead Software Engineer |
| **Dependencies** | [Security Principles](../07-Security/SECURITY-PRINCIPLES.md), [CI/CD Plan](CI-CD-PLAN.md), [Threat Model](../07-Security/THREAT-MODEL.md) |
| **Update Process** | Update when package manager is selected (OQ-001) and when license is decided (OQ-010). |

---

## 1. Principles

- Minimise dependencies — every dependency is a supply chain risk
- Prefer well-maintained, widely-used packages
- All dependencies must have compatible licenses
- Vulnerabilities are tracked and resolved before merge
- Lock files are committed to ensure reproducible builds

---

## 2. Dependency Approval

### Before Adding a Dependency

Contributor must verify:

| Check | Requirement |
|-------|-------------|
| **Necessity** | Cannot be reasonably implemented in-house within PR scope |
| **License** | Compatible with project license (OQ-010) |
| **Maintenance** | Active maintenance; last release within 12 months |
| **Security history** | No unresolved Critical vulnerabilities |
| **Size** | Bundle size impact acceptable |
| **Alternatives** | Simpler alternative considered and documented in PR |

### Approval Process

| Dependency Type | Approval |
|-----------------|----------|
| Dev/test tooling | Lead Software Engineer |
| Runtime dependency | Lead Software Engineer + PR review |
| Security-sensitive (crypto, auth, networking) | Project Owner review |
| AI/ML model or library | Project Owner review |

Document new dependencies in the PR description with justification.

---

## 3. Vulnerability Checking

### Automated Scanning

| When | Action |
|------|--------|
| Every PR | CI dependency audit (when configured) |
| Weekly | Scheduled vulnerability scan |
| Before release | Full audit; no Critical or High unresolved |

### Response Times

| Severity | Action | Timeline |
|----------|--------|----------|
| Critical | Block merge; fix or remove immediately | Before any merge |
| High | Fix before next release | Current or next sprint |
| Medium | Track in tech-debt issue | Within 2 sprints |
| Low | Track in backlog | Best effort |

## 4. Lock File Policy

| Rule | Detail |
|------|--------|
| **Lock files committed** | Yes — `pnpm-lock.yaml` and `Cargo.lock` committed (DEC-012) |
| **Lock file updates** | Intentional only — update when adding/upgrading dependencies |
| **Lock file in PR review** | Reviewers check for unexpected dependency changes |
| **Specific manager** | Determined when stack is selected (OQ-001, OQ-019) |

Current `.gitignore` has lock file entries commented out pending this policy. When stack is selected, uncomment the appropriate lock file and commit it.

## 5. Supply Chain Considerations

### Prohibited

- Packages with no source repository or opaque distribution
- Packages requiring post-install scripts that execute arbitrary code (without review)
- Dependencies with license incompatibilities
- Unpinned dependencies in production code (`*` or `latest` version ranges)

### Recommended

- Pin exact versions or use lock files
- Prefer packages from reputable publishers
- Review changelogs before upgrading major versions
- Maintain a dependency inventory (generated by package manager)

### AI/ML Dependencies

If AI model libraries are added (OQ-004):

- Review data handling behaviour of the library
- Verify no telemetry or phone-home without opt-in
- Document model file sources and checksums
- Prefer local inference libraries over remote SDKs for MVP

Pending OQ-010 resolution. Interim rules:

| License Type | Status |
|--------------|--------|
| MIT, Apache 2.0, BSD | Generally acceptable |
| GPL, AGPL | Requires Project Owner approval — may affect project license |
| Proprietary | Prohibited unless explicitly approved |
| Unknown / No license | Prohibited |

Run license audit as part of CI when tooling is available.

---

## 7. Monorepo Dependency Management

When monorepo tooling is selected (OQ-019):

- Shared dependencies hoisted where possible
- Per-package dependencies declared in package manifest
- No duplicate versions of the same library without justification
- Workspace-level scripts for audit and update
